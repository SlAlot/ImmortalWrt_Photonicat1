# eMMC 自动扩容与配置恢复记录

## 本次问题

2026-10-27 真机的 eMMC 实际约 58.3 GiB，根分区却只有 1 GiB，扣除 SquashFS 后 `/overlay` 约 891 MiB。Docker 宿主镜像占用约 800 MiB，导致配置分区满。网心云缓存已映射到 TF 卡，但宿主镜像仍在 eMMC。

启动日志明确记录：

```text
mount_root: mount failed: No space left on device
mount_root: switching to f2fs failed - fallback to ramoverlay
```

系统因此使用 `/tmp/root`，显示默认配置；原配置仍在 `/overlay/upper`。本次已完整备份配置和 Docker 数据，恢复原配置，并暂将 Docker 数据保存在 TF 卡上的 ext4 文件中。没有格式化 TF 卡，也没有清除网心云缓存。没有证据确认 Wi-Fi 设置直接触发配置丢失，最初重启的原因仍未确认。

## 固件修复

- 镜像保留 1 GiB 初始分区，首次开机在 overlay 挂载前自动扩展 eMMC 根分区和文件系统，适配官方 1+8、2+16、4+64 GB 机型。运行内存不变。
- 使用连续空闲空间，遇到额外数据分区即停止，不移动或覆盖用户数据分区。
- 全新 SquashFS 的配置分区由 fstools 按扩展后的容量初始化；已有 F2FS 离线扩展，ext4 同时支持。后续开机按容量判断，已扩展时不重复操作。
- 不设置 Docker 容量配额，不增加存储警告弹窗或 Docker 启动限制。默认原生 `/overlay/docker` 路径继续使用，已有数据及自定义路径不自动迁移。
- 标准 sysupgrade 允许相同起点、根分区容量更大的布局，保留扩容后的分区边界。不同分区布局仍按上游流程处理。配置备份不包含 Docker 镜像、容器和数据卷，升级前需要另行备份这些数据。

预启动脚本和工具必须编译到固件的只读系统内。仅向已经运行的旧版系统复制文件，不能完成挂载前的 F2FS 扩容；旧固件需升级后生效。首次启动如内核无法立即重新读取分区容量，会自动重启一次再完成扩展。

## 验证范围

隔离 Linux 环境对稀疏虚拟磁盘执行实际分区调整和文件系统扩展，覆盖 8 / 16 / 64 GiB、真机 64GB 容量、非整 MiB 容量、全新与已有 F2FS、ext4、额外数据分区、挂载状态和重启续跑，共 15 项。核对配置文件内容、文件系统 UUID、非零启动代码、RK Loader、其他分区内容与重复执行结果。另有升级布局比较和构建补丁检查。

此前整套 126 项 Linux 回归通过、无跳过。本次复核补充根挂载可选字段兼容，扩容专项 21 项通过、无跳过，包含上述 15 项磁盘测试；相关 Shell 检查通过，正式发布仍须通过 Actions 全套回归与成品检查。这些结果不等于已在每种容量的光影猫上刷机验收。现场机器恢复了持久配置，但旧版固件尚未扩容，需要刷入新版后生效。
